With offline support turned on, the React UI Kit keeps working when the network drops. Chats and messages the user has already opened load from a cache on the device at once, messages sent while offline wait in a queue and go out when the connection returns, and every list says plainly when something needs a connection.

The UI Kit builds on [offline support in the JavaScript SDK](/sdk/javascript/offline-overview). You turn it on once in `UIKitSettings`; the components handle the rest.

## Overview

**Works offline**

- Conversations, users, groups, group members, messages, reactions, notifications, and pinned and saved messages the user has already loaded appear straight away from the cache.
- Messages the user sends (text, media, custom and stickers) are queued and sent automatically on reconnect.
- Media that was downloaded while online is shown from the device.
- When the connection returns, the SDK catches up on what was missed and the lists update in place.

**Needs a connection**

- Anything the user has never opened while online, for example the first load of a chat or a list.
- Keyword search with no saved match, and the Search screen.
- Edits, deletes, reactions and other actions on messages that are already sent. They are not queued. (Retry and Delete on a message that is not sent yet work offline.)
- Calls, call logs, message information and AI features such as streamed replies.

## Requirements

| Requirement | Version |
| --- | --- |
| React UI Kit | `@cometchat/chat-uikit-react` **7.3.0** or later |
| JavaScript Chat SDK | `@cometchat/chat-sdk-javascript` **4.3.0** or later |
| React | 18 or later (the UI Kit's peer range is `>=18.0.0 <21.0.0`) |

The UI Kit's peer dependency on the Chat SDK stays `^4.2.0`, so upgrading the UI Kit does not force an SDK upgrade. On an SDK older than 4.3.0, `setOfflineConfig()` has no effect and the UI Kit works online as before. Install 4.3.0 or later to use offline support:

```bash
npm install @cometchat/chat-uikit-react@^7.3.0 @cometchat/chat-sdk-javascript@^4.3.0
```

Offline support is for UI Kit v7 only. UI Kit v6 and earlier have no offline UI, and turning on the SDK's offline support with them is not supported.

For the browsers and storage the SDK uses for its cache, see [Supported runtimes](/sdk/javascript/offline-enable#supported-runtimes).

## Enable Offline Support

Offline support is **off by default**. Call `setOfflineConfig()` on the `UIKitSettingsBuilder` before `CometChatUIKit.init()`, and set `enabled: true`.

```tsx title="src/main.tsx"
import ReactDOM from "react-dom/client";
import { CometChatUIKit, UIKitSettingsBuilder } from "@cometchat/chat-uikit-react";
import App from "./App";

const settings = new UIKitSettingsBuilder()
  .setAppId("APP_ID")
  .setRegion("REGION")
  .setAuthKey("AUTH_KEY")
  .subscribePresenceForAllUsers()
  .setOfflineConfig({
    enabled: true,
    // Optional. Every key below has a default in the SDK:
    // maxPendingMessages: 50,
    // mediaCaching: "AUTO",
    // encryption: true,
  })
  .build();

CometChatUIKit.init(settings).then(async () => {
  await CometChatUIKit.login("cometchat-uid-1");
  ReactDOM.createRoot(document.getElementById("root")!).render(<App />);
});
```

The UI Kit passes the object to the SDK's `AppSettingsBuilder.setOfflineConfig()` unchanged. Its type, `CometChatOfflineConfig`, is exported from `@cometchat/chat-uikit-react` and lists the same keys as the SDK's `OfflineConfig`, so a misspelled key is a compile error. For what each key does and its default (cache size, outbox size, media caching, encryption and so on), see [OfflineConfig options](/sdk/javascript/offline-reference#offlineconfig-options).

<Note>
Offline turns on only for an explicit `enabled: true`. If you don't call `setOfflineConfig()`, or pass a config without `enabled: true`, the UI Kit behaves exactly as it does today.
</Note>

Whether offline support is actually running can change after init. For example, it is off before anyone logs in, and when the encrypted cache cannot open. To check it in your own code, call `CometChat.isOfflineEnabled()` at the moment you need the answer rather than reading back the config you passed. See [Verify it is active](/sdk/javascript/offline-enable).

## How the Components Behave Offline

### Lists

[Conversations](/ui-kit/react/components/conversations), [Users](/ui-kit/react/components/users), [Groups](/ui-kit/react/components/groups), [Group Members](/ui-kit/react/components/group-members), [Reaction List](/ui-kit/react/components/reaction-list), [Notification Feed](/ui-kit/react/components/notification-feed), [Pinned Messages](/ui-kit/react/components/pinned-messages) and [Saved Messages](/ui-kit/react/components/saved-messages) all load in two steps:

1. The saved rows paint first, from the cache.
2. The server's page then replaces them in place when it arrives.

When a load can't reach the server:

| Situation | What the list shows | `onError` |
| --- | --- | --- |
| Rows are on screen, offline | The rows stay. No error view. | Not called |
| Nothing on screen, offline | An icon and "Connect to load chats" (or users, groups, members, messages, reactions, notifications), with no Retry button. The list loads again once by itself on reconnect. | Called once |
| Nothing on screen, offline, keyword search | "Connect to search" with a second line, "Search needs an internet connection." The search runs again once on reconnect. | Not called |
| Nothing on screen, online, a real error | The usual error view. It does not reload by itself. | Called |
| The server answered with nothing | The usual empty view | Not called |

A list opened with only a filter (for example online users only, tags, or a request builder with no keyword) is a plain list, not a search. Offline with nothing saved, it says "Connect to load …", never "Connect to search".

If you pass your own `errorView` (or `emptyView` for a keyword search), your view is shown instead of the offline state. See [Customization](#customization).

### Search

The [Search](/ui-kit/react/components/search) component needs a connection for keyword search:

- Offline, with nothing shown, a keyword search shows "Connect to search" and "Search needs an internet connection."
- A search by filter alone is answered from the device. With nothing saved it shows the plain "No results" state, with no `onError`.
- When both conversation and message results fail and at least one failure is a real error (not a lost connection), the error view shows and `onError` is called.

### Message list and threads

- A chat opens with its cached messages, then the server's page merges in.
- A chat opened offline with nothing saved shows "Connect to load messages". It is read again once when the connection returns.
- At an edge the cache can't fill (older history, or newer messages after jumping to a message), the list shows a "Connect to load more" row. The row is a button, and it also loads by itself once when the connection returns.
- Jumping to a message (from a search result, a quoted reply or the first unread message) works offline when that message is saved. If it isn't, the chat opens on its newest saved messages instead.
- After a long outage the catch-up may bring more than a page of new messages. While the user is reading older messages, a **Jump to latest** button appears instead of moving the list.

<Warning>
The default message list asks the server for pages in the form the SDK caches, then applies its message types, categories and hide-deleted setting on the device. If you pass your own `messagesRequestBuilder`, it is sent as you built it, and its pages are cached only when `hideReplies` is its only content filter.
</Warning>

### Composer and sending

- A message sent while offline appears in the list at once with a clock icon and the label "Not sent yet". It is sent automatically when the connection returns, and its receipt then updates as usual.
- A message that fails shows an error mark and a **Not sent. Tap to retry** button under the bubble. The failed state survives a page reload.
- The message menu of an unsent or failed message offers only **Retry** and **Delete**. Actions that need a server copy (reply, edit, react and so on) are hidden until it is sent. **Delete** removes the message from this device. It is hidden when `hideDeleteMessageOption` is set.
- Retry or Delete on a message whose send is already under way changes nothing and shows "Sending… try again in a moment".
- If the outbox is full, the send is refused and the list shows "Too many messages waiting to send". A file larger than the media cache limit is refused with "File too large to send offline". See [Queue limits](/sdk/javascript/offline-send#queue-limits).
- In the [attachment staging tray](/ui-kit/react/components/message-composer#multi-attachment-staging-tray), a file whose upload stopped because the connection dropped is not treated as a bad file: pressing Send queues it with the rest of the message.
- Voice notes, stickers and the group call message queue like any other send.

### Media

With media caching on (the SDK default), images, videos, audio and files that were downloaded while online are shown from the device. A media bubble whose file is not saved shows "Available when online" while the device is offline. Tapping it asks the SDK to download the file, and the bubble updates once it is saved. See [Media Caching](/sdk/javascript/offline-media-caching).

### Edits, deletes and reactions

These are not queued. They are sent as soon as the user acts, and they fail if there is no connection:

- **Reactions** show at once, then roll back and call the message list's `onError` if the request fails.
- **Deleting** a sent message calls `onError` if it fails, and the message stays.
- **Editing** a message: the composer clears and leaves edit mode when the user sends the edit. If the edit fails, the message keeps its old text and `onError` is called.

See [Edits, Deletes, and Reactions Need a Connection](/sdk/javascript/offline-send#edits-deletes-and-reactions-need-a-connection).

### Presence

While the SDK is disconnected, nobody shows as online: no online dot, no "Online" subtitle and no typing indicator, in any list or header, and screen readers are told the same. Presence comes back after the reconnect.

### Logout, user switch and cache reset

The cache is per user. A logout or a switch to another user clears every list on screen, and the SDK deletes that user's cached data and queued messages.

If the SDK has to wipe and rebuild its cache (for example when the encryption key is lost), every mounted list reloads. If unsent messages were lost, a notice such as "2 unsent messages couldn't be recovered" appears once, in the Conversations list or the open Message List. See [When the cache resets](/sdk/javascript/offline-sync#when-the-cache-resets).

```tsx
import { CometChatLocalize } from "@cometchat/chat-uikit-react";

const localize = CometChatLocalize.getSharedInstance();
localize?.addTranslation("en-us", {
  conversations_connect_to_load: "You're offline. Chats will load when you reconnect.",
  message_list_not_sent_yet: "Waiting for network",
});
```

## Errors and Callbacks

### `onError`

- **Rows on screen:** offline, a failed load is silent (no error view, no `onError`). A real error calls `onError` once when the user or your app started the load (opening the list, refreshing, searching, paging), and stays silent when the UI Kit started it (reconnect, coming back to the foreground, sync).
- **Nothing on screen:** see the [Lists](#lists) table.
- **Actions:** a failed reaction, delete or edit calls `onError`, as above.

### Send promises

`CometChatUIKit.sendTextMessage()`, `sendMediaMessage()` and `sendCustomMessage()` answer every send:

- Queueing a message does not reject the promise. It resolves when the message is sent and rejects on a final failure.
- A logout or user switch, a cache reset that loses the unsent messages, or the SDK removing the message rejects the promise once with an error whose `code` is `ERROR_OFFLINE_MESSAGE_DISCARDED`.
- The UI Kit shows nothing for that rejection: no error toast, no `onError`, and the composer does not lock. Only your own `.catch` hears of it.

```tsx
import { CometChat } from "@cometchat/chat-sdk-javascript";
import { CometChatUIKit } from "@cometchat/chat-uikit-react";

const message = new CometChat.TextMessage("cometchat-uid-2", "Hello!", CometChat.RECEIVER_TYPE.USER);

CometChatUIKit.sendTextMessage(message)
  .then((sent) => console.log("Sent", sent.getId()))
  .catch((error) => {
    if (error?.code === "ERROR_OFFLINE_MESSAGE_DISCARDED") {
      // Logged out, switched user or cache reset before it could send.
      return;
    }
    console.error("Send failed", error);
  });
```

With offline off, these methods behave as before.

### Events

Two UI events are added to the [event system](/ui-kit/react/event-system). Both fire only with offline support on.

| Event | Payload | When |
| --- | --- | --- |
| `ui:message/send-state-changed` | `{ message, state, reason? }` | An own message's send state changed. `state` is a `CometChatMessageSendState`: `"sending"` (queued or in flight), `"sent"`, `"failed"` (Retry offered) or `"discarded"` (removed before it was sent). `reason` is the SDK's `MessageFailureReason` for `failed` and `discarded`. Fired once per change per message. |
| `ui:offline/cache-reset` | `{ reason, pendingMessagesLost }` | The SDK wiped and rebuilt its cache. Every mounted list reloads. `pendingMessagesLost` is the number of unsent messages that could not be kept, or `null` when unknown. |

`ui:message/sent` keeps its meaning and still fires for each send.

```tsx
import { useCometChatEvents } from "@cometchat/chat-uikit-react";

function OfflineSendTracker() {
  useCometChatEvents((event) => {
    switch (event.type) {
      case "ui:message/send-state-changed":
        console.log(event.message.getMuid(), event.state, event.reason);
        break;
      case "ui:offline/cache-reset":
        console.log("Cache reset", event.reason, event.pendingMessagesLost);
        break;
      default:
        break;
    }
  }, []);

  return null;
}
```

<Warning>
These events are new members of the exported `CometChatEvent` union. If your TypeScript code has an exhaustive `switch` on `event.type` with no `default`, add one.
</Warning>

## Customization

### Hide the offline notices

| Component | Prop | Default | Hides |
| --- | --- | --- | --- |
| [Message List](/ui-kit/react/components/message-list) | `hideOfflineNotices` | `false` | The notices about unsent messages: removed, not sent, lost in a cache reset, outbox full, file too large, send under way |
| [Conversations](/ui-kit/react/components/conversations) | `hideOfflineNotices` | `false` | The notice shown after a cache reset lost, or may have lost, unsent messages |

```tsx
<CometChatMessageList user={user} hideOfflineNotices />
<CometChatConversations hideOfflineNotices />
```

### Use your own offline view

The lists show your own `errorView` instead of "Connect to load …", and your own `emptyView` instead of "Connect to search". To tell the offline state apart inside your view, read `connectToLoad` or `connectToSearch` from the component's context hook. They are `true` only while the offline state is shown, and never set with offline off.

| Context hook | `connectToLoad` | `connectToSearch` |
| --- | --- | --- |
| `useCometChatConversationsContext` | Yes | Yes |
| `useCometChatUsersContext` | Yes | Yes |
| `useCometChatGroupsContext` | Yes | Yes |
| `useCometChatGroupMembersContext` | Yes | Yes |
| `useCometChatReactionListContext` | Yes | No |
| `useCometChatNotificationFeedContext` | Yes | No |
| `useCometChatPinnedMessagesContext` | Yes | No |
| `useCometChatSavedMessagesContext` | Yes | No |
| `useCometChatSearchContext` | No | Yes |

## With Offline Support Turned Off

Apps that don't call `setOfflineConfig()` get no offline UI, no offline events and no change to how sends work. A few fixes in the same release do change what every app sees:

- A message list that is empty when the connection returns now loads again and shows its empty state, instead of staying blank.
- A reconnect while the newest message is still unsent now fetches the messages missed during the outage.
- Paging past a conversation that just received a message no longer shows it twice.
- A `messagesRequestBuilder` you pass to `CometChatMessageList` or `CometChatSavedMessages` is no longer modified.
- Saved Messages rows are no longer announced to screen readers as selectable options.
- Message rows, conversation rows, notices, the composer input and the empty and error views carry new `data-cc` attributes for test automation. Existing `data-testid` and `data-message-id` attributes are kept, but DOM snapshot tests may change.

## Limitations and Known Issues

- **Only what was loaded online is saved.** A user who has never opened a chat or list while online has nothing to show offline.
- **Thread replies opened online are not saved for offline.** Replies sent or received on this device are saved.
- **A lost send acknowledgement can create one duplicate** of that message on the server.
- **Missed messages can take up to about 10 seconds** to appear after a quick reconnect.
- **After a page reload, a failed message's reason may be unknown.** It is still offered Retry.
- **A chat can stall while online** if a send got no answer while connected. It resumes at the next reconnect.
- **Multiple tabs:** a cache rebuild in one tab can discard another tab's unsent messages. That tab's rows update to match.
- **Need a connection:** keyword search, message information, call logs and AI streamed replies. Call logs have no saved copy and keep their own error view.
- **Encryption in the browser** covers the cached content but not its lookup metadata, and downloaded media is stored unencrypted. See [Encrypt the Cache](/sdk/javascript/offline-encryption).
