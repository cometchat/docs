If your users or developers sit behind a corporate firewall, web proxy, or VPN that
restricts outbound traffic, add the CometChat domains below to your allowlist so chat,
calling, and media work. All of it is **outbound** traffic (HTTPS/WSS plus the few ports listed
under [Ports](#ports)) — there are no inbound connections to open.

<Note>
**Allow by domain, not by IP.** CometChat runs on elastic cloud infrastructure, so its IP
addresses change without notice and IP-pinning will eventually break your integration. If
your security policy requires fixed IP ranges, [contact CometChat](https://help.cometchat.com/) —
they are provided on request, not published, because they are not static.
</Note>

## Quickest option — allow two domains

Allowing these two wildcard domains — together with the outbound [ports](#ports) below — is enough for CometChat to work end to end:

```text
*.cometchat.io
*.cometchat.com
```

- **`*.cometchat.io`** — all runtime traffic: the chat API and SDK, the realtime WebSocket,
  calling, and media. This is the one your end users' network must allow.
- **`*.cometchat.com`** — the dashboard and developer/support tooling (used by your team, not
  by end users at runtime).

If wildcards are acceptable in your policy, you can stop here. The sections below are for
teams that must allowlist individual subdomains.

## Allow by purpose (granular)

`<region>` is your app's data region — **`us`**, **`eu`**, or **`in`** (find it in your app's
endpoint on the [Dashboard](https://app.cometchat.com/)), and `<appId>` is your App ID. Allow
only the region(s) your apps run in.

### Runtime — chat and calling

Allow these per region (`<region>` = `us`, `eu`, or `in`), replacing `<appId>` with your App ID:

| Domain | Purpose |
| --- | --- |
| `api-<region>.cometchat.io`, `<appId>.api-<region>.cometchat.io` | Chat REST API |
| `apiclient-<region>.cometchat.io`, `<appId>.apiclient-<region>.cometchat.io` | SDK client API |
| `websocket-<region>.cometchat.io`, `<appId>.websocket-<region>.cometchat.io`, `ws-<region>.cometchat.io` | Realtime WebSocket — live messages, typing, presence |
| `rtc-<region>.cometchat.io`, `rtc-web-<region>.cometchat.io`, `call-<region>.cometchat.io` | Voice and video calling (WebRTC media and the Calls REST API) |
| `data-<region>.cometchat.io`, `assets.cometchat.io` | Media and attachments (images, files, audio, video, avatars) and static SDK/UI Kit assets |
| `metrics-<region>.cometchat.io` | Usage metrics |

### Widget and dashboard

| Domain | Purpose |
| --- | --- |
| `widget-js.cometchat.io` | Chat Widget script |
| `app.cometchat.com`, `app.cometchat.io` | CometChat Dashboard — create apps, view credentials, change settings |

### Ports

Open these **outbound**:

| Protocol | Port(s) | Purpose |
| --- | --- | --- |
| TCP | 80, 443 | HTTP / HTTPS — API, call signaling, and the realtime WebSocket (WSS) |
| TCP | 5222, 7443 | Chat connection |
| UDP | 10000–20000 | Voice / video media (WebRTC) — the required minimum is UDP 10000; the [Calls Network Requirements](/calls/platform/compatibility) recommend the full 10000–20000 range, with TCP 443 as fallback |

<Warning>
Realtime chat and calling need more than port 443. A proxy that blocks or buffers **WebSocket (WSS)**
upgrades, or a firewall that blocks **UDP 10000–20000**, is the most common cause of a client stuck
on "connecting" or a call that rings but has no audio/video. If your firewall must pin destinations,
the media / TURN IP ranges are provided by CometChat on request — [contact us](https://help.cometchat.com/);
they are not a published, static set.
</Warning>

### Developer and support tooling (your team, not end users)

These are `*.cometchat.com` and are used by your team, not by end users at runtime:

| Domain | Purpose |
| --- | --- |
| `app.cometchat.com` | CometChat Dashboard (also listed above) |
| `api-explorer.cometchat.com` | Interactive REST API explorer |
| `www.cometchat.com` | Documentation (`/docs`) and website |
| `help.cometchat.com` | Support portal |
| `status.cometchat.com` | Service status page |

### Push notifications (delivered by Google and Apple)

Push is delivered through the platform providers, so allow **their** domains, not a CometChat one:

- **FCM** (Android / Web) — Google's push endpoints, e.g. `fcm.googleapis.com`.
- **APNs** (iOS) — Apple's push endpoints, e.g. `api.push.apple.com`.

See each platform's own network requirements for the authoritative, complete list.

## Installing the SDKs (build and CI networks)

The domains above are for **running** the app. If your build or CI network is also locked down,
the CometChat packages are pulled from the standard registries plus CometChat's package host:

| Platform | Fetched from |
| --- | --- |
| Web / React / Angular / React Native | `registry.npmjs.org` |
| Android (UI Kit / Calls SDK) | Maven Central and `dl.cloudsmith.io` |
| iOS (UI Kit / Calls SDK) | GitHub (CocoaPods / Swift Package Manager) and `dl.cloudsmith.io` |
| Flutter | `pub.dev` |

`dl.cloudsmith.io` (path `/public/cometchat/cometchat`) hosts the iOS and Android binaries and
the React Native calls library.

## Notes

- **All required traffic is outbound** (see [Ports](#ports)). No inbound firewall rules are required for CometChat.
- **Region scoping:** allow the `-<region>` subdomains for your app's region; allow `us`, `eu`, and
  `in` together only if you operate apps in more than one region.
- **On-premise deployments** host these services on your own domains instead — see
  [On-Premise Deployment](/on-premise-deployment/docker/overview).
- Check the [status page](https://status.cometchat.com/) if traffic is allowed but a service still
  seems unreachable.
