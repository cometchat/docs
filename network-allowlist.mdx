If your users or developers sit behind a corporate firewall, web proxy, or VPN that restricts
outbound traffic, add the CometChat domains below to your allowlist so chat, calling, AI agents,
moderation, and media work. All of it is **outbound** traffic (HTTPS/WSS plus the few ports listed
under [Ports](#ports)) — there are no inbound connections to open.

<Note>
**Allow by domain, not by IP.** CometChat runs on elastic cloud infrastructure, so its IP addresses
change without notice and IP-pinning will eventually break your integration. If your security policy
requires fixed IP ranges, [contact CometChat](https://help.cometchat.com/) — they are provided on
request, not published, because they are not static.
</Note>

## The domain families

CometChat serves traffic from **four** domains. Most runtime services run on the first three (for
redundancy and edge routing), so allow all three; `cometchat.com` carries the dashboard and website.

| Domain | Used for |
| --- | --- |
| `cometchat.io` | Primary runtime + media + CDN + tooling |
| `cc-cluster-2.io` | Runtime (cluster routing) — same services as above |
| `cc-edge-2.io` | Runtime (edge routing) — same services as above |
| `cometchat.com` | Dashboard, preview, support, status, website |

## Quickest option — allow the wildcards

Allowing these wildcard domains — together with the outbound [ports](#ports) below — is enough for
CometChat to work end to end:

```text
*.cometchat.io
*.cc-cluster-2.io
*.cc-edge-2.io
*.cometchat.com

# apex domains too (a *.x rule usually does not cover bare x)
cometchat.io
cc-cluster-2.io
cc-edge-2.io
cometchat.com
```

<Warning>
Some proxies treat `*.cometchat.io` as matching only one label deep, but several CometChat hosts are
deeper (e.g. `<appId>.api-<region>.cometchat.io` is three labels under the apex). If your firewall
matches only one level, use its "match all subdomains / any depth" option (or add `*.*.cometchat.io`)
so per-app hosts aren't missed. The same applies to `cc-cluster-2.io` and `cc-edge-2.io`.
</Warning>

If wildcards are acceptable in your policy, you can stop here. The sections below list every
individual host for teams that must allowlist per-subdomain.

## Full per-service list

`<region>` is your app's data region — **`us`**, **`eu`**, or **`in`** (find it in your app's endpoint
on the [Dashboard](https://app.cometchat.com/)); `<appId>` is your App ID. Allow only the region(s)
your apps run in. Where a service lists three families, allow all three.

### Runtime — chat, calling, AI, moderation

Each of these runs on all three runtime families — `cometchat.io`, `cc-cluster-2.io`, `cc-edge-2.io`:

| Service | Host pattern (× each runtime family) |
| --- | --- |
| Admin APIs | `<appId>.api-<region>.<family>` |
| Client APIs | `<appId>.apiclient-<region>.<family>` |
| Calls APIs | `<appId>.call-<region>.<family>` |
| AI Agent Service | `<appId>.ai-agent-service-<region>.<family>` |
| WebSockets (realtime) | `<appId>.websocket-<region>.<family>` |
| Moderation | `<appId>.rule-<region>.<family>` |

So, for example, Admin APIs = `<appId>.api-<region>.cometchat.io`, `<appId>.api-<region>.cc-cluster-2.io`,
and `<appId>.api-<region>.cc-edge-2.io`.

| --- | --- |

| Legacy WebSockets | `<appId>.ws-<region>.cometchat.io` |

## Ports

Open these **outbound**:

| Protocol | Port(s) | Purpose |
| --- | --- | --- |
| TCP | 80, 443 | HTTP / HTTPS — APIs, call signaling, and the realtime WebSocket (WSS) |
| TCP | 5222, 7443 | Chat connection |
| UDP | 10000–20000 | Voice / video media (WebRTC) — the required minimum is UDP 10000; the [Calls Network Requirements](/calls/platform/compatibility) recommend the full 10000–20000 range, with TCP 443 as fallback |

<Warning>
Realtime chat and calling need more than port 443. A proxy that blocks or buffers **WebSocket (WSS)**
upgrades, or a firewall that blocks **UDP 10000–20000**, is the most common cause of a client stuck on
"connecting" or a call that rings but has no audio/video. If your firewall must pin destinations, the
media / TURN IP ranges are provided by CometChat on request — [contact us](https://help.cometchat.com/);
they are not a published, static set.
</Warning>

## Push notifications (delivered by Google and Apple)

Push is delivered through the platform providers, so allow **their** domains, not a CometChat one:

- **FCM** (Android / Web) — Google's push endpoints, e.g. `fcm.googleapis.com`.
- **APNs** (iOS) — Apple's push endpoints, e.g. `api.push.apple.com`.

See each platform's own network requirements for the authoritative, complete list.

## Installing the SDKs (build and CI networks)

The domains above are for **running** the app. If your build or CI network is also locked down, the
CometChat packages are pulled from the standard registries plus CometChat's package host:

| Platform | Fetched from |
| --- | --- |
| Web / React / Angular / React Native | `registry.npmjs.org` |
| Android (UI Kit / Calls SDK) | Maven Central and `dl.cloudsmith.io` |
| iOS (UI Kit / Calls SDK) | GitHub (CocoaPods / Swift Package Manager) and `dl.cloudsmith.io` |
| Flutter | `pub.dev` |

`dl.cloudsmith.io` (path `/public/cometchat/cometchat`) hosts the iOS and Android binaries and the
React Native calls library.

## Notes

- **All required traffic is outbound** (see [Ports](#ports)). No inbound firewall rules are required
  for CometChat.
- **Region scoping:** allow the `-<region>` subdomains for your app's region; allow `us`, `eu`, and
  `in` together only if you operate apps in more than one region.
- **On-premise deployments** host these services on your own domains instead — see
  [On-Premise Deployment](/on-premise-deployment/docker/overview).
- Check the [status page](https://status.cometchat.com/) if traffic is allowed but a service still
  seems unreachable.
