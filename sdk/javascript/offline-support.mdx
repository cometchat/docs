Offline support keeps a local copy of the logged-in user's conversations and messages on the device. Your app can render that copy the moment a screen opens — with or without a network — and the SDK replaces it with fresh server data as soon as it arrives. Messages sent while the device is offline are saved in a queue (the outbox) and sent automatically when the connection returns.

Offline support is **opt-in**. Until you enable it, the SDK behaves exactly as it does today: nothing is stored on the device and every read goes to the server.

## How It Works

- **One local store per user.** The SDK keeps a separate store for each app ID and user, in the browser's IndexedDB. Logging out, or logging in as a different user, deletes the previous user's store.
- **Cached, then server.** When you pass a listener to a read such as `fetchPrevious()`, the SDK first hands you what it has cached, then the server's result. Every server result is written back to the cache.
- **Queued sends.** A message sent with a `MessageSentListener` is stored in the outbox first. If the device is offline, it stays queued and is sent automatically once the connection is back.
- **Catch-up sync.** After a reconnect, the SDK sends queued messages, then refreshes the cached conversations and messages so changes made while you were offline (new, edited and deleted messages) reach the cache.
- **The server wins.** If the cached copy and the server copy of a message differ, the server copy is kept.

## Enable Offline Support

Pass an offline configuration to `setOfflineConfig()` on the `AppSettingsBuilder`, then initialize the SDK as usual. Always include `enabled: true`.

<Tabs>
  <Tab title="TypeScript">
    ```typescript
    let appID: string = "APP_ID";
    let region: string = "APP_REGION";

    let appSetting: CometChat.AppSettings = new CometChat.AppSettingsBuilder()
      .subscribePresenceForAllUsers()
      .setRegion(region)
      .setOfflineConfig({
        enabled: true,
        maxPendingMessages: 50,
        mediaCaching: CometChat.MediaCachingMode.AUTO,
      })
      .build();

    CometChat.init(appID, appSetting).then(
      (initialized: boolean) => {
        console.log("Initialization completed successfully", initialized);
      },
      (error: CometChat.CometChatException) => {
        console.log("Initialization failed with error:", error);
      }
    );
    ```
  </Tab>

### Configuration Options

Set `enabled: true` to turn offline support on. Every other option is optional, and anything you leave out uses its default. The count limits accept the range shown; a value outside it, including `0`, is treated as the maximum.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `enabled` | `boolean` | `false` | Set `enabled: true` to turn offline support on. Nothing is stored on the device unless offline support is on. |
| `maxPendingMessages` | `number` | `50` | How many messages the outbox can hold. Range 1–100. |
| `pendingQueueOverflowPolicy` | `CometChat.PendingMessageOverflowPolicy` | `REJECT_NEWEST` | What happens when the outbox is full: `REJECT_NEWEST` rejects the new send, `DROP_OLDEST` marks the oldest queued message as failed to make room. |
| `autoSendPendingOnReconnect` | `boolean` | `true` | Sends queued messages automatically after a reconnect. When `false`, a queued message is sent only when you call `retryMessage()` for it or a new message is sent in the same conversation. It does not affect the catch-up sync. |
| `mediaCaching` | `CometChat.MediaCachingMode` | `AUTO` | `AUTO` downloads attachments of fetched and received messages so they can be viewed offline. `OFF` caches the message and its attachment details but not the file itself. |
| `maxMediaCacheSize` | `number` (bytes) | `524288000` (500 MB) | Space cached media may use. The least recently used files are removed first. `0` means no limit. |
| `maxStorageSize` | `number` (bytes) | `262144000` (250 MB) | Space the cached conversations and messages may use. The oldest messages are removed first. `0` means no limit. |
| `maxConversations` | `number` | `100` | How many conversations the cache keeps. The least recently used conversation is removed first, with its messages. Range 1–1000. |
| `maxMessagesPerConversation` | `number` | `500` | How many of the latest messages the cache keeps for each conversation. Range 1–1000. |
| `cacheDurationDays` | `number` (days) | `0` | Removes a cached conversation that has had no new message and hasn't been opened for this many days. `0` means no time limit. |
| `maxSnapshotQueries` | `number` | `100` | How many different list requests — users, groups, members and the other [lists](#other-lists), each with its own filters — are kept for offline use. The least recently used is removed first. Range 1–1000. |
| `snapshotTtlDays` | `number` (days) | `7` | How long a cached list request stays available offline. After that it returns nothing offline until it is loaded online again. `0` means no time limit. |
| `encryption` | `boolean` | `false` | Encrypts the cached data at rest. See [Encrypt the Cache](#encrypt-the-cache). |
| `encryptionFailureBehavior` | `string` | `"ONLINE_ONLY"` | Applies only when `encryption` is `true` and encryption can't run on the device. `"ONLINE_ONLY"` opens no cache and the app works online only. `"PLAINTEXT_FALLBACK"` opens an unencrypted cache so offline support keeps working. |

Messages waiting in the outbox, including failed ones, are never removed by these limits.

## Check Whether Offline Is Running

`CometChat.isOfflineEnabled()` returns `true` only while offline support is actually running for the logged-in user: you enabled it, a user is logged in, and the local store is open. It returns `false` before login, after logout, and when CometChat has switched offline support off for your app. Read it each time you need it instead of storing the value.

<Tabs>
  <Tab title="TypeScript">
    ```typescript
    let offlineRunning: boolean = CometChat.isOfflineEnabled();
    ```
  </Tab>
  <Tab title="JavaScript">
    ```javascript
    let offlineRunning = CometChat.isOfflineEnabled();
    ```
  </Tab>
</Tabs>

CometChat can turn offline support off for an app from the server. When that happens, the SDK stops using the local store, deletes the cached data and `isOfflineEnabled()` returns `false`. Your app keeps working online.

## Read From the Cache, Then the Server

Pass a fetch listener to a request's `fetchPrevious()` or `fetchNext()` to receive results in two steps:

1. `onCached*` — what is stored on the device, delivered immediately. It can be an empty list.
2. `onServer*` — the server's result, which also updates the cache. If the device is offline, or the request fails, `onError` is called instead.

The call still returns a Promise that settles with the server result, so handle the outcome in one place. Without a listener, the request reads from the server only, exactly as before.

### Messages

<Tabs>
  <Tab title="TypeScript">

    ```typescript
    let UID: string = "UID";

    let messagesRequest: CometChat.MessagesRequest =
      new CometChat.MessagesRequestBuilder()
        .setUID(UID)
        .setLimit(limit)
        .build();

    messagesRequest
      .fetchPrevious(
        new CometChat.MessageFetchListener({

            // Render the cached page right away

            // Replace it with the server's page

          onError: (error: CometChat.CometChatException) => {

        // Already handled in onError
    ```

### Other Lists

The same pattern works for these requests:

| Request | Listener | Callbacks |
| --- | --- | --- |
| `UsersRequest`, `BlockedUsersRequest` | `CometChat.UserFetchListener` | `onCachedUsers` · `onServerUsers` · `onError` |
| `GroupsRequest` | `CometChat.GroupFetchListener` | `onCachedGroups` · `onServerGroups` · `onError` |
| `GroupMembersRequest` | `CometChat.GroupMemberFetchListener` | `onCachedGroupMembers` · `onServerGroupMembers` · `onError` |
| `BannedMembersRequest` | `CometChat.BannedMemberFetchListener` | `onCachedBannedMembers` · `onServerBannedMembers` · `onError` |
| `ReactionsRequest` | `CometChat.ReactionFetchListener` | `onCachedReactions` · `onServerReactions` · `onError` |
| `NotificationFeedRequest` | `CometChat.NotificationFeedFetchListener` | `onCachedNotificationFeedItems` · `onServerNotificationFeedItems` · `onError` |

These lists are served from the cache only for a request that was loaded online before with the same filters. A list that has never been loaded online has nothing to show offline.

### When the Cache Is Skipped

The cache only answers a request when it can apply every filter on the request correctly. If a request uses a filter that only the server can evaluate — for example `setSearchKeyword()` — `onCached*` is not called and only the server answers. The cache phase is also skipped while offline support is not running.

## Send Messages While Offline

Pass a `MessageSentListener` as the second argument to `sendMessage()`, `sendMediaMessage()` or `sendCustomMessage()`. The listener has three callbacks:

| Callback | When it fires |
| --- | --- |
| `onMessagePending(message)` | The message is saved in the outbox. Show it in the UI as pending. |
| `onMessageSent(message)` | The server accepted the message. Replace the pending copy with this one. |
| `onError(error)` | The send failed, or the device is offline (see below). |

<Tabs>
  <Tab title="TypeScript">
    ```typescript
    let receiverID: string = "UID";
    let receiverType: string = CometChat.RECEIVER_TYPE.USER;
    let textMessage: CometChat.TextMessage = new CometChat.TextMessage(
      receiverID,
      "Hello",
      receiverType
    );

    CometChat.sendMessage(
      textMessage,
      new CometChat.MessageSentListener({
        onMessagePending: (message: CometChat.BaseMessage) => {
          // Show the message with a pending indicator
        },
        onMessageSent: (message: CometChat.BaseMessage) => {
          // Swap the pending copy for the sent message
        },
        onError: (error: CometChat.CometChatException) => {
          // Offline: the message is still queued and will be sent on reconnect
        },
      })
    ).catch(() => {
      // Already handled in the listener
    });
    ```
  </Tab>
  <Tab title="JavaScript">
    ```javascript
    let receiverID = "UID";
    let receiverType = CometChat.RECEIVER_TYPE.USER;
    let textMessage = new CometChat.TextMessage(receiverID, "Hello", receiverType);

      textMessage,
      new CometChat.MessageSentListener({

          // Swap the pending copy for the sent message
        },
        onError: (error) => {
          // Offline: the message is still queued and will be sent on reconnect
        },
      })
    ).catch(() => {
      // Already handled in the listener
    });
    ```
  </Tab>
</Tabs>

What happens depends on the connection:

- **Online:** `onMessagePending`, then `onMessageSent`. The Promise resolves with the sent message.
- **Offline:** `onMessagePending`, then `onError` once with the code `FAILED_TO_FETCH`, and the Promise rejects. The message is **not** lost — it stays in the outbox and is sent after the connection returns, when `onMessageSent` fires. Do not resend it yourself, or the recipient receives it twice.
- **Outbox full:** with the default `REJECT_NEWEST` policy, the new send fails with `onError` (code `QUEUE_FULL`), the Promise rejects and the message is not saved.
- **Rejected later:** if a queued message can't be sent once the connection is back, it is marked as failed. While the page that sent it is still open, `onError` is called again with the reason. See [Failed Messages and Retry](#failed-messages-and-retry).

<Warning>
  Only sends that pass a `MessageSentListener` are queued. A send without a
  listener behaves exactly as before: while offline, its Promise rejects and
  the message is not saved.
</Warning>

Use `message.getLocalMessageId()` to match the pending message to the sent one. The SDK assigns this ID when the message is queued; it is separate from any `muid` you set.

### Get Pending Messages

`CometChat.getPendingMessages()` resolves with the messages that are still in the outbox, including failed ones. Pass a conversation ID (`message.getConversationId()`) to get only that conversation's messages. Use it to show queued messages again after a page reload.

### Failed Messages and Retry

`message.getStatus()` on a message from the outbox returns one of these `CometChat.MessageStatus` values:

| Status | Meaning |
| --- | --- |
| `PENDING` | Queued. It is sent automatically when the device is connected. |
| `SENDING` | Being sent now. |
| `FAILED` | It could not be sent. It stays in the outbox until you retry it. |

A queued message becomes `FAILED` when:

- the server rejects it — for example, the receiver can't be messaged, the request isn't allowed, or the rate limit is exceeded;
- the request keeps failing without a response from the server — the SDK retries it in the background a few times with an increasing delay first;
- it is dropped from a full outbox by the `DROP_OLDEST` policy.

The SDK never retries a `FAILED` message on its own. Retry it from your UI, for example from a "tap to retry" action:

| Method | Description |
| --- | --- |
| `CometChat.retryMessage(message: BaseMessage \| string, listener?: MessageSentListener): Promise<void>` | Queues one message again. Pass the message, or its `getLocalMessageId()`. |
| `CometChat.retryAllFailedMessages(listener?: MessageSentListener): Promise<void>` | Queues again every message that failed without a server response. Messages the server rejected, and messages dropped by `DROP_OLDEST`, are skipped; retry those one at a time with `retryMessage()`. |

<Tabs>
  <Tab title="TypeScript">
    ```typescript
    CometChat.getPendingMessages().then((messages: CometChat.BaseMessage[]) => {
      messages
        .filter((message) => message.getStatus() === CometChat.MessageStatus.FAILED)
        .forEach((message) => {
          CometChat.retryMessage(message);
        });
    });
    ```
  </Tab>
  <Tab title="JavaScript">
    ```javascript
    CometChat.getPendingMessages().then((messages) => {
      messages
        .filter((message) => message.getStatus() === CometChat.MessageStatus.FAILED)
        .forEach((message) => {
          CometChat.retryMessage(message);
        });
    });
    ```
  </Tab>
</Tabs>

A retried message is sent right away when the device is connected, and otherwise on the next reconnect. Read its status with `getPendingMessages()` to update your UI.

## Listen for Sync Events

After a reconnect, the SDK runs a catch-up sync in two phases: conversations, then messages. Register a `SyncListener` to know when each phase starts, finishes or fails — for example, to refresh a screen once the sync is complete.

<Tabs>
  <Tab title="TypeScript">
    ```typescript
    let listenerID: string = "UNIQUE_LISTENER_ID";

    CometChat.addSyncListener(
      listenerID,
      new CometChat.SyncListener({
        onConversationSyncStarted: () => {},
        onConversationSyncCompleted: () => {
          // Re-fetch the conversation list
        },
        onConversationSyncError: (error: CometChat.CometChatException) => {},
        onMessageSyncStarted: () => {},
        onMessageSyncCompleted: () => {
          // Re-fetch the open message list
        },
        onMessageSyncError: (error: CometChat.CometChatException) => {},
      })
    );

    // Remove it when you no longer need it
    CometChat.removeSyncListener(listenerID);
    ```
  </Tab>
  <Tab title="JavaScript">
    ```javascript

          // Re-fetch the conversation list
    ```

### Updates Picked Up by the Sync

The catch-up sync also tells your existing `MessageListener` what changed while the device was offline. Messages that are new to the device arrive through `onMessageReceived` as usual (for example `onTextMessageReceived`). Edits, deletions and other changes to messages that were already cached arrive together in `onMessagesSynced`. Update the matching messages in your UI by ID instead of appending them.

    ```typescript
        },
      })
    );
    ```

    ```typescript
      .setRegion("APP_REGION")
      .setOfflineConfig({ enabled: true, encryption: true })
      .build();
    ```
  </Tab>
  <Tab title="JavaScript">

`CometChat.getOfflineEncryptionStatus()` reports what is actually in effect — `enabled` is what you asked for, and `atRest`, `keyStorage` and `cipherAvailable` describe what the SDK achieved. If encryption can't run on the device, the default `encryptionFailureBehavior` of `"ONLINE_ONLY"` keeps offline support off, so the app works online only and nothing unencrypted is written. Set it to `"PLAINTEXT_FALLBACK"` if you prefer an unencrypted cache in that case; `atRest` then reports `"NONE"`.

In the browser, keep these limits in mind:

- Encryption needs the Web Crypto API, which browsers provide only in a secure context: a page served over HTTPS, from `localhost`, or opened from a `file://` URL. On a plain `http://` address such as a LAN IP, encryption can't run.
- Message content is encrypted field by field, and the key is kept in the same browser storage as the data. This protects against casual inspection of the stored data, not against code running on your page or someone with access to the browser profile.
- Cached media files are not encrypted. Set `mediaCaching: CometChat.MediaCachingMode.OFF` to stop caching received attachments; attachments you send are still stored until they are sent.

This is not end-to-end encryption; it only affects the copy stored on the device.

## Logging Out and Switching Users

The SDK deletes the local store — cached data, cached media and queued messages — when the user logs out. Queued messages are discarded without a callback. Logging in as a different user deletes the previous user's store before the new one opens. Do not clear the cache yourself on logout.

## Limitations

- The cache holds what your app has loaded while online, plus the changes picked up by the catch-up sync. Older history that was never loaded is not available offline.
- Only messages sent with a `MessageSentListener` are queued offline. Other actions — such as editing, deleting, reacting, pinning or marking as read — need a connection.
- Queued messages are discarded on logout.
- Cached data counts toward the browser's storage quota for your site, and the browser can clear it.

## Browser Notes

- **Iframes.** Some browsers, including Safari, partition storage by the top-level site. If your chat runs in an iframe embedded on another site, its cache is separate from the cache of the same app opened directly. An iframe sandboxed without `allow-same-origin` has no access to storage, and the SDK can't run there.
- **Multiple tabs.** All tabs of your app on the same site share one local store. If several tabs are open when the connection returns, a message queued while offline can occasionally be delivered more than once.

## Electron

{/* TODO(release): publish this section only after the SDK's Electron IPC path-validation fix ships. Remove this comment and the section if that fix is not in the release. */}

In an Electron app, the SDK can store the cache in an SQLite database and cached media as files in the app's user data folder, instead of in IndexedDB. Set it up in the main process and the preload script:

1. Install `better-sqlite3-multiple-ciphers`, built for your Electron version. It is required for SQLite storage and for encryption. Without it, the SDK uses IndexedDB, as in a browser; with `encryption: true`, `encryptionFailureBehavior` decides what happens.
2. In the main process, call `registerOfflineIpc()` once the app is ready, and create the window with `contextIsolation: true`.
3. In the preload script, call `installCometChatBridge()`.

<Tabs>
  <Tab title="main.js">
    ```javascript
    const { app, BrowserWindow } = require("electron");
    const path = require("path");
    const { registerOfflineIpc } = require("@cometchat/chat-sdk-javascript/electron/main");

    app.whenReady().then(() => {
      registerOfflineIpc();

      new BrowserWindow({
        webPreferences: {
          preload: path.join(__dirname, "preload.js"),
          contextIsolation: true,
          nodeIntegration: false,
          sandbox: false, // or bundle the preload script; see the note below
        },
      });
    });
    ```
  </Tab>
  <Tab title="preload.js">
    ```javascript
    const { installCometChatBridge } = require("@cometchat/chat-sdk-javascript/electron/preload");

    installCometChatBridge();
    ```
  </Tab>
</Tabs>

<Note>
  Electron sandboxes the preload script by default (`sandbox: true`), and a
  sandboxed preload can't load modules from `node_modules`. Either set
  `sandbox: false` for the window, or bundle your preload script, including
  the SDK's preload module, into a single file. If the preload doesn't load,
  the SDK falls back to IndexedDB.
</Note>

With encryption on, the whole SQLite database is encrypted and its key is protected by the operating system's key store. On Linux this needs a keyring service; without one, encryption can't run.
