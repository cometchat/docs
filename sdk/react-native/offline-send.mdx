| Field | Value |
| --- | --- |
| Send | `CometChat.sendMessage(message, listener)` — also `sendMediaMessage`, `sendCustomMessage`, `sendInteractiveMessage` |
| Listener | `MessageSentListener`: `onMessagePending` → `onMessageSent` or `onError(error, reason)` |
| Message state | `message.getLocalMessageId()`, `message.getMessageStatus()`, `message.getFailureReason()` |

```typescript
CometChat.sendMessage(textMessage, {
  onMessagePending: (message) => { /* getMessageStatus() === PENDING, fires immediately */ },
  onMessageSent: (message) => { /* server ack: real id + sentAt */ },
  onError: (error, reason) => { /* reason == null: queued, not failed. reason set: real failure */ },
});

const localId = message.getLocalMessageId();
const status = message.getMessageStatus();     // PENDING | SENDING | SENT | DELIVERED | READ | FAILED
const why = message.getFailureReason();        // set only while FAILED

await CometChat.getPendingMessages();          // PENDING + SENDING + FAILED
await CometChat.retryMessage(localId);
await CometChat.retryAllFailedMessages();      // transient failures only
await CometChat.discardLocalMessage(localId);  // delete an unsent message
```

</Accordion>

With offline support enabled, a message you send while the device has no connection is **durably queued on the device** instead of failing. It keeps its place across an app restart and is sent automatically when the connection returns. This page shows the offline-aware send listener, how to read a message's status, how to inspect and recover the send queue, and the queue limits.

<Note>
Offline support is **off by default** and requires SDK **4.2.0** or newer. Queuing only happens once you [enable it](/sdk/react-native/offline-enable); with offline off, a send over no connection fails exactly as before.
</Note>

## Send a Message

Pass a `MessageSentListener` as the second argument to `sendMessage`. Its lifecycle is `onMessagePending` first (the message is durably queued), then exactly one final outcome — `onMessageSent` (the server accepted it) or, for a real failure, `onError`.

<Tabs>
<Tab title="TypeScript">
```typescript
const textMessage: CometChat.TextMessage = new CometChat.TextMessage(
  "UID",
  "Hello!",
  CometChat.RECEIVER_TYPE.USER
);

CometChat.sendMessage(textMessage, {
  onMessagePending: (message: CometChat.BaseMessage) => {
    // Queued and persisted; message.getMessageStatus() === CometChat.MessageStatus.PENDING
    console.log("Pending, local id:", message.getLocalMessageId());
  },
  onMessageSent: (message: CometChat.BaseMessage) => {
    // Server ack: message now carries its real id and sentAt
    console.log("Sent:", message.getId());
  },
  onError: (error: CometChat.CometChatException, reason?: CometChat.MessageFailureReason | null) => {
    // reason == null: queued, not failed. Otherwise a real failure.
    console.log("Send error:", error.code, reason);
  },
});
```
</Tab>


The same `MessageSentListener` is accepted by all four send methods:

```typescript
CometChat.sendMessage(textMessage, listener);                  // TextMessage
CometChat.sendMediaMessage(mediaMessage, listener);            // MediaMessage
CometChat.sendCustomMessage(customMessage, listener);          // CustomMessage
CometChat.sendInteractiveMessage(interactiveMessage, listener); // InteractiveMessage
```

<Note>
Passing a listener does not change the return value — each method still returns its Promise, and the Promise settles on the server outcome. Consume the final result from **one** channel, the Promise or the listener, not both. `onMessagePending` fires only while offline support is active.
</Note>

## Queued, Not Failed

When the device is offline, the send still fires `onMessagePending`, then fires `onError` **once** with the not-connected error: code `FAILED_TO_FETCH`, `errorParams.queued === true`, and `reason` equal to `null`. The Promise rejects with the same error. This is a **notification, not a failure**: the message stays durably `PENDING`, and `onMessageSent` fires **later**, on reconnect, when it actually goes. Do not send it again.

So for a single send, `onError` and `onMessageSent` can **both** fire (offline, then reconnect), and `onError` does not always mean the message failed. Use `reason` (or `error.errorParams.queued`) to tell the two apart:

| `onError` arguments | Meaning | What to do |
|---|---|---|
| `reason == null`, `error.errorParams.queued === true` | Queued; not sent yet. Will auto-send on reconnect. | Show as sending/queued; nothing to do. |
| `reason` is a `MessageFailureReason` | A real failure; will not retry on its own. | Offer the user a manual retry (see below). |

<Tabs>
<Tab title="TypeScript">
```typescript
onError: (error: CometChat.CometChatException, reason?: CometChat.MessageFailureReason | null) => {
  if (reason == null) {
    // Queued offline — auto-sends on reconnect
  } else {
    // Real failure — surface a retry action
  }
},
```
</Tab>
<Tab title="JavaScript">
```javascript
onError: (error, reason) => {
  if (reason == null) {
    // Queued offline — auto-sends on reconnect
  } else {
    // Real failure — surface a retry action
  }
},
```
</Tab>

### Message status and failure reason

Every message exposes its offline state. `getLocalMessageId()` returns the SDK-generated handle that is stamped at compose (while offline is running) and stays stable across the whole lifecycle — use it to retry or discard the message.

| Accessor | Type | Notes |
|---|---|---|
| `getLocalMessageId()` | `string \| undefined` | Client handle; present while offline is running. |
| `getMessageStatus()` | `MessageStatus` | `PENDING`, `SENDING`, `SENT`, `DELIVERED`, `READ`, `FAILED`. |
| `getFailureReason()` | `MessageFailureReason \| undefined` | Set only while `FAILED`; otherwise `undefined`. |

<Warning>
Read the offline status with `getMessageStatus()`. `BaseMessage.getStatus()` is the existing call/message status field and is **not** the offline status.
</Warning>

`MessageFailureReason` values:

| Reason | When |
|---|---|
| `TRANSIENT` | A temporary server error (for example 5xx or rate-limited), or no answer after 5 reconnect attempts in a row. Retryable. |
| `PERMANENT` | The server rejected the message, or the error was not recognized. A manual retry will not help. |
| `QUEUE_FULL` | A new send was refused because the queue is full (count cap). |
| `QUEUE_OVERFLOW` | An older queued message was evicted to admit a newer one (`DROP_OLDEST` only). |
| `BYTE_OVERFLOW` | A media send was refused because it exceeds the queue's byte budget. |
| `DISCARDED` | The message was removed before it could send (for example `clearOfflineCache()`). |

## Inspect the Queue

`getPendingMessages` returns the **entire un-acked outbox** — every `PENDING`, `SENDING`, and `FAILED` message, ordered by local compose time. Sent messages are not included. Read each message's status to group them. It returns an empty list when offline support is off.

<Tabs>
<Tab title="TypeScript">
```typescript
CometChat.getPendingMessages().then(
  (messages: CometChat.BaseMessage[]) => {
    messages.forEach((m) => console.log(m.getLocalMessageId(), "->", m.getMessageStatus()));
  },
  (error: CometChat.CometChatException) => {
    console.log("Could not read the outbox:", error.code);
  }
);
```
</Tab>
<Tab title="JavaScript">
```javascript
CometChat.getPendingMessages().then(
  (messages) => {
    messages.forEach((m) => console.log(m.getLocalMessageId(), "->", m.getMessageStatus()));
  },
  (error) => {
    console.log("Could not read the outbox:", error.code);
  }
);
```
</Tab>
</Tabs>

If the local store is briefly unavailable, the call rejects with `ERROR_OFFLINE_MESSAGE_PERSIST_FAILED` rather than returning an empty list — try again.

### Observe the queue app-wide

The per-call `MessageSentListener` lives only as long as the call. To watch every queue transition — a live send, a reconnect auto-flush, a manual retry, or a resumed send after an app restart — register a global `OfflineMessageListener`. Its failed callback carries the `MessageFailureReason`.

<Tabs>
<Tab title="TypeScript">
```typescript
CometChat.addOfflineMessageListener("LISTENER_ID", {
  onOutboxMessagePending: (message: CometChat.BaseMessage) => {},
  onOutboxMessageSent: (message: CometChat.BaseMessage) => {},
  onOutboxMessageFailed: (message: CometChat.BaseMessage, reason: CometChat.MessageFailureReason) => {
    console.log("Failed:", message.getLocalMessageId(), reason);
  },
});

// Remove it when no longer needed
CometChat.removeOfflineMessageListener("LISTENER_ID");
```
</Tab>
<Tab title="JavaScript">
```javascript
CometChat.addOfflineMessageListener("LISTENER_ID", {
  onOutboxMessagePending: (message) => {},
  onOutboxMessageSent: (message) => {},
  onOutboxMessageFailed: (message, reason) => {
    console.log("Failed:", message.getLocalMessageId(), reason);
  },
});

// Remove it when no longer needed
CometChat.removeOfflineMessageListener("LISTENER_ID");
```
</Tab>
</Tabs>

## Retry and Discard

There is no automatic retry of a `FAILED` message — recovery is explicit and user-invoked. Use the message's local id. Each method takes an optional listener as a second argument; omit it and you get a Promise instead (never both).

- **`retryMessage(localMessageId)`** re-attempts one message. A `FAILED` message is reset to `PENDING` and sent; a `PENDING` message is attempted now rather than waiting for a reconnect. The result is that attempt's outcome.
- **`retryAllFailedMessages()`** retries **transient** failures only; permanent ones are skipped. The Promise form resolves once the retries are issued; pass a `MessageSentListener` to see each outcome.
- **`discardLocalMessage(localMessageId)`** deletes an unsent (`PENDING` or `FAILED`) message from the device, including its copied media. The discard's own listener (`DiscardMessageListener`) gets `onSuccess(localMessageId)`; the original send's listener is released with no final outcome.

<Tabs>
<Tab title="TypeScript">
```typescript
await CometChat.retryMessage(localMessageId);

await CometChat.retryAllFailedMessages();

CometChat.discardLocalMessage(localMessageId).then(
  () => console.log("Discarded"),
  (error: CometChat.CometChatException) => console.log("Discard rejected:", error.code)
);
```
</Tab>
<Tab title="JavaScript">
```javascript
await CometChat.retryMessage(localMessageId);

await CometChat.retryAllFailedMessages();

CometChat.discardLocalMessage(localMessageId).then(
  () => console.log("Discarded"),
  (error) => console.log("Discard rejected:", error.code)
);
```
</Tab>
</Tabs>

`retryMessage` and `discardLocalMessage` reject, changing nothing, when:

| Error code | Reason |
|---|---|
| `ERROR_OFFLINE_MESSAGE_IN_FLIGHT` | The message is already sending (`SENDING`). |
| `ERROR_OFFLINE_MESSAGE_NOT_FOUND` | No unsent message has that id (unknown, or already sent). |
| `ERROR_OFFLINE_DISABLED` | Offline support is not running. |
| `ERROR_OFFLINE_MESSAGE_PERSIST_FAILED` | The local cache was briefly unavailable. Try again. |

These codes are available as `CometChat.OfflineErrorCode.MESSAGE_IN_FLIGHT`, `MESSAGE_NOT_FOUND`, `DISABLED` and `MESSAGE_PERSIST_FAILED`.

## Auto-send on Reconnect

By default, queued `PENDING` messages are sent automatically when the realtime connection is re-established. This is controlled by `OfflineConfig.autoSendPendingOnReconnect` (default `true`); see [Enable Offline Support](/sdk/react-native/offline-enable) and the [reference](/sdk/react-native/offline-reference). With it off, nothing retries a queued message on reconnect — a send that gets no answer becomes `FAILED` (`TRANSIENT`), which you recover with `retryMessage`.

Reconnect also runs a catch-up sync for received messages — see [Stay in Sync](/sdk/react-native/offline-sync).

## Queue Limits

The outbox holds at most `maxPendingMessages` messages still trying to send (`PENDING` + `SENDING`); `FAILED` messages do not count. When the queue is full, `OfflineConfig.pendingQueueOverflowPolicy` decides what happens:

| `PendingMessageOverflowPolicy` | Behaviour on overflow |
|---|---|
| `REJECT_NEWEST` (**default**) | The new send is refused and reported with reason `QUEUE_FULL`. Nothing already queued is lost. |
| `DROP_OLDEST` | The oldest `PENDING` message is evicted (reason `QUEUE_OVERFLOW`) to admit the new one. |

A media send that exceeds the queue's byte budget is refused with reason `BYTE_OVERFLOW`.

A **refused** send (`QUEUE_FULL` / `BYTE_OVERFLOW`) is never queued, so it fires **no** `onMessagePending`; it reports `onError` with the code `ERROR_PENDING_QUEUE_LIMIT`, and the global `OfflineMessageListener` receives `onOutboxMessageFailed(message, reason)` carrying the exact reason.

<Warning>
A refused or evicted message (`QUEUE_FULL`, `QUEUE_OVERFLOW`, `BYTE_OVERFLOW`) has **no durable row** — it does not appear in `getPendingMessages`, and calling `retryMessage` on its id does nothing. Capture these from the failure callback and handle them at that moment. Prefer the default `REJECT_NEWEST`, which never silently drops an already-queued message from another conversation.
</Warning>

## Edits, Deletes, and Reactions Need a Connection

Offline queuing applies to **sending new messages** only. Changes to existing messages — edit, delete, add or remove a reaction — and other own actions are **not queued offline**. They are sent to the server whenever you trigger them, and they reject with the not-connected error if the request gets no answer. Their effect reaches the cache only once the server accepts them.

## Durable Media Uploads

A multi-attachment upload survives an app restart: the SDK re-attaches to an in-progress batch instead of restarting it. Fetch the existing request for a conversation with `getExistingUploadFileRequest` (a Promise that resolves `null` when there is none), and read each file's progress through `getItems()`, which returns a list of items, each with a `state` of `QUEUED`, `UPLOADING`, `UPLOADED`, `FAILED`, or `REJECTED` (which cannot be retried). Retry an individual file with `retryAttachment(fileId)`. With offline on, each item also carries `localCopyPath`, the SDK's copy of the bytes, for previews of a restored tray.

<Tabs>
<Tab title="TypeScript">
```typescript
const request = await CometChat.getExistingUploadFileRequest("UID", CometChat.RECEIVER_TYPE.USER);

request?.getItems().forEach((item) => {
  console.log(item.fileId, "->", item.state);
  if (item.state === "FAILED") {
    request.retryAttachment(item.fileId);
  }
});
```
</Tab>
<Tab title="JavaScript">
