Offline support keeps the logged-in user's conversations and messages on the device so your app can show them instantly, lets the user send messages while disconnected, and catches up automatically when the connection returns. It is **off by default** — nothing changes in your app until you enable it ([Enable Offline Support](/sdk/flutter/offline-enable)). This page explains the mental model; the other pages show the exact APIs.

<Note>
Offline support requires CometChat Flutter SDK **5.1.0** or later.
</Note>

## How it works

Three ideas carry the whole feature.

<Steps>
<Step title="Cache first, then server">
Every read goes through the local cache first. For list reads the SDK delivers the cached page immediately, even when it is empty. Single-item lookups (`getMessageDetails`, `getConversation`) deliver a cached result only when that item is already cached. The SDK then fetches from the server and delivers the fresh result. Your UI renders what is on the device without waiting for the network, then updates when the server responds. See [Show Cached Data](/sdk/flutter/offline-cached-data).
</Step>
<Step title="A durable send outbox">
A message sent while offline is saved to a durable outbox and reported as pending instead of failing. It survives app restarts and is sent when the connection returns. See [Send While Offline](/sdk/flutter/offline-send).
</Step>
<Step title="Catch up on reconnect">
When the device reconnects, the SDK syncs the conversations and messages that changed while it was away and flushes the outbox, so the local cache matches the server again. See [Stay in Sync](/sdk/flutter/offline-sync).
</Step>
</Steps>

```mermaid
flowchart LR
    A[App read] --> B[(Local cache)]
    B -- cached page first --> A
    B --> C{Online?}
    C -- yes --> D[Server]
    D -- fresh result --> A
    C -- no --> E[onError:\nERR_CONNECTION]
    F[Send while offline] --> G[(Durable outbox)]
    G -- on reconnect --> D
```

## What changes in your app

With offline support enabled, your fetch and send callbacks fire **twice** on the read path and gain a pending stage on the send path. To receive these cached and pending results, pass a `listener:` to the fetch and send methods — `MessageFetchListener`, `ConversationFetchListener`, `MessageSentListener`, and the others listed on each page. The `onSuccess`/`onError` form of the same method keeps working: it receives only the server result, and a send through it is never queued. With offline support off, every API behaves exactly as it did before.

## One cache per user

The SDK keeps a single local cache for the user who is logged in.

- The cache survives app restarts while the same user stays logged in, so the data is there instantly on next launch.
- Logging out, a session expiring, or logging in as a **different** user wipes the cache, including any unsent messages still in the outbox, which are lost. You never clear it yourself — the SDK does it.

See [Stay in Sync](/sdk/flutter/offline-sync) for cache resets and logout behaviour.

## How much is kept

By default the cache is bounded by size, not age: it holds up to **100 conversations**, up to **500 messages per conversation**, around **250 MB** of data, and up to **500 MB** of cached media. Older entries are evicted first as these limits are reached. Every limit is tunable — see the [Configuration & API Reference](/sdk/flutter/offline-reference).
